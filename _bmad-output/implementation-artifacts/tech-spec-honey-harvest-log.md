# Tech-Spec: Honey Harvest Log

**Created:** 2026-05-16

## Overview

### Problem Statement

There is no way to record honey harvests in the app. Manuel needs to log when and how much honey was harvested from each hive (in kg, decimal values), with an optional free-text notes field, including while offline in the field.

### Solution

Add a new `honey_harvests` DB table with offline deduplication support (`clientId`), a scoped create form at `/hives/[hiveId]/harvests/new`, a global harvest log at `/harvests`, and a JSON API endpoint at `/api/harvests` for offline sync. Follows the stings incident pattern throughout.

### Scope

**In Scope:**
- New `honey_harvests` DB table: `hiveId` (required FK → hives, cascade delete), `harvestedAt` (Unix epoch), `amountKg` (real, decimal), `notes` (nullable text), `clientId` (UUID, offline dedup unique index), `createdAt`, `updatedAt`
- `honeyHarvests.ts` query file: create, list-all-with-hive-name (left join), get-by-id, delete
- `/hives/[hiveId]/harvests/new` — create form scoped to a hive
- `/harvests` — global harvest log, all hives, ordered by date descending, inline delete with modal
- `/harvests/new` — create form with hive selector (mirrors `/stings/new`), used when navigating from the global log
- `/api/harvests` — GET (list) + POST (offline sync), mirrors `/api/stings`
- Offline: new `harvests-outbox` IndexedDB store; `DB_VERSION` bumped 1 → 2; sync loop added to `sync.ts`; `pendingSync` store updated to count both outboxes
- Nav link `Ernten` added to `+layout.svelte`
- `+ Neue Ernte` button added to hive detail CTA section

**Out of Scope:**
- Edit form (create + delete only)
- Harvest detail page
- Per-hive harvest sub-list page (global `/harvests` covers all hives)
- Totals / charts / statistics

### Technical Decisions

- **`amountKg` as `real`**: Drizzle's `real()` maps to SQLite REAL — natively supports decimals like `11.4`. The HTML input uses `type="number" step="0.1" min="0.1"`. Server-side parsing uses `parseFloat()`. Server-side validation: must be `> 0` and `<= 9999` (max reasonable single harvest). Both the form action (T7) and the API endpoint (T3) must enforce this range.
- **`hiveId` required (not nullable)**: Every harvest is always tied to a specific hive. The hive-scoped create form (`/hives/[hiveId]/harvests/new`) has no hive selector. The global create form (`/harvests/new`) shows a hive selector dropdown using `getActiveHives()`.
- **`clientId` initialisation**: Use `let clientId = $state(crypto.randomUUID())` — the `$state` initialiser runs once on component creation. **Do NOT use `$effect()`** to set `clientId`; effects re-run on re-renders and would regenerate the UUID, silently breaking offline dedup.
- **Separate IndexedDB store**: The `'outbox'` store is tightly coupled to the inspection data shape (`OutboxEntry` interface). Harvests get their own `'harvests-outbox'` store with a `HarvestOutboxEntry` interface. **Before bumping `DB_VERSION` to 2**, verify the current value in `src/lib/client/offline/db.ts` — if it has already been incremented beyond 1 for any reason, bump to `current + 1` instead. The existing store is preserved because the `contains()` guard is kept.
- **`HarvestOutboxEntry` interface** (define in `db.ts`, used by T4, T6, T8): `{ clientId: string; hiveId: number; harvestedAt: number; amountKg: number; notes: string | null; syncStatus: 'pending' | 'syncing' | 'error'; createdAt: number; }` — `clientId` is the `keyPath`. All timestamps are Unix epoch seconds.
- **Delete on list page**: No harvest detail page. The named action `delete` lives on `harvests/+page.server.ts`, identical to how `stings/+page.server.ts` handles deletion.
- **`/api/harvests` flat (not hive-scoped)**: Follows `/api/stings` pattern. `hiveId` is in the JSON body. Simpler offline sync — one fixed endpoint URL.
- **`onConflictDoNothing()` for dedup**: `createHarvestEntry` uses `.onConflictDoNothing().returning().get()` — returns `undefined` if `clientId` already exists. API returns `json({ duplicate: true }, { status: 200 })`. The sync loop removes the IDB entry on any 2xx (`res.ok`) — body content is never inspected by the sync client, so 200 and 201 are both treated as success.
- **API validation edge cases** (T3 POST): `hiveId` missing or not a number → `error(400, { message: '...' })`; `amountKg` missing, not a number, `<= 0`, or `> 9999` → `error(400, ...)`; `hiveId` referencing a non-existent hive will throw a SQLite FK violation — catch it and return `error(400, { message: 'Hive not found' })` rather than letting a 500 propagate. Malformed JSON body → `error(400, { message: 'Invalid JSON' })`.
- **Sync error retry**: Entries stuck at `syncStatus: 'error'` are retried on every sync trigger (app open, online event, visibility change). There is no retry cap — this is consistent with the existing inspection sync behaviour. A permanently malformed entry would loop forever; this is an accepted limitation for V1 (same as inspections).
- **`updatedAt` reserved**: Defined in schema for future edit support (not in V1 scope). No update query function is created now. Set to the same value as `createdAt` on insert.
- **Cascade delete is intentional**: Deleting a hive cascades to `honey_harvests`, consistent with the `inspections` table. Historical harvest data is considered part of the hive's lifecycle. No changes to the hive delete flow are required.
